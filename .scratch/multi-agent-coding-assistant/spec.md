# Spec：多 Agent 编码助手（图编排）

## Problem Statement

作为在本地仓库工作的开发者，我可以用自然语言描述编码目标，但当工作需要分工角色、并行模块设计、显式冲突处理，以及安全的并行改码时，单一 agent loop 容易失控或踩踏。我需要一个助手：把目标变成可协调的多 Agent 工作流——先写薄共享契约，再按模块并行设计并在冲突时合并，写码用隔离 worktree，在设计冻结与最终合并前设置人闸，并以可验证结果收尾（PR 草稿 + 检查通过 + Review 通过）——而不是变成无治理的多 Agent 群聊。

## Solution

一个面向当前仓库的本地 CLI / 对话驱动编码助手。Orchestrator 在固定的六类角色 org graph 上生成本次 work graph。系统把可审计产物写入 `runs/<run-id>/`，在设计冻结后与最终合并/接受 PR 前暂停等人批准；写操作在每任务独立的 git worktree/分支上执行；设计冲突先靠结构化字段 + 确定性 diff 检出，再经 LLM 调和，僵持则升级给人；成功标准为：PR 草稿 + 约定检查通过 + Reviewer 未阻断。

架构遵循 Graph Engineering：可编程的 org graph + 每次请求的 work graph + 共享状态；每个节点内部可跑自己的 agent loop；路由与扇出/扇入显式定义——不以自由群聊为主对齐手段。

## User Stories

2. 作为开发者，我想用自然语言表达编码目标，以便开工前不必手工拆成一堆票据。
3. 作为开发者，我想让助手为本请求生成 work graph，以便并行与串行步骤清晰可审计。
4. 作为开发者，我想在模块设计之前先产出薄共享契约，以便并行设计者共享边界、接口与非目标。
5. 作为开发者，我想按模块 ownership 并行做模块设计，以便独立模块能提高设计吞吐。
6. 作为开发者，我想自动检出冲突的模块设计，以便不兼容的 API 或权属主张在写码前暴露。
7. 作为开发者，我想要 Reconciler 提出合并后的冻结设计，以便不必手工 diff 每一份设计文档。

9. 作为开发者，我想在设计冻结后设置硬闸，以便未批准设计不会启动写码 worktree。
10. 作为开发者，我想在 CLI 里批准或驳回冻结设计，以便 run 可暂停/恢复且不丢状态。
11. 作为开发者，我想让 Implementer 按写任务使用隔离 git worktree/分支，以便并行编辑不污染共享工作树。
12. 作为开发者，我想在安全时共享只读调研与读代码上下文，以便设计/发现更快且不引入写冲突。

## Implementation Decisions

- 用 Python 实现本地编码助手；对外入口为 `run`（CLI 包装同一库 API）。
- 用 LangGraph 作为编排运行时：节点、边、扇出/扇入、共享状态、人机 checkpoint。智能节点内部可用 agent loop（Deep Agents / `create_agent` 等可作节点内 harness；不能替代显式的设计扇出/合并拓扑）。
- v1 固定 org graph 角色种类：
  - Orchestrator — 生成本次 work graph；不写大段设计或生产代码。
  - Contracts — 产出薄共享契约（边界、接口、数据实体、错误语义、非目标）。
  - Module-Designers — 按模块动态扇出；各写模块设计，不改生产代码。
  - Reconciler — 检出冲突，合并为冻结设计；重大分歧升级到人闸。
  - Implementers — 按实现任务扇出到隔离 worktree/分支；只读探索可共享上下文。
  - Reviewer — 审 diff、跑约定检查、通过或打回责任 Implementer；不做功能级大重写。
- 人闸（硬闸）：(1) 设计冻结之后、任何实现写 worktree 之前；(2) 最终合并/接受 PR 草稿之前。CLI 必须支持在这些闸门上暂停/恢复。
- 工作区策略：混合隔离——读/调研可共享；每个写任务必须隔离 worktree/分支。
- 完成定义：PR 草稿（或等价可审 diff 包）+ 配置的检查通过 + Reviewer 未阻断。合入 main 由人闸控制，不是 v1 的自动成功条件。
- 产物布局：主真相源为 `runs/<run-id>/`，至少包含契约、各模块设计、冲突报告、冻结设计、任务拆分、PR 元数据。可选镜像到 `.scratch/<feature>/` 以便晋升到 issue tracker；不要把 backlog 票据和原始 run 痕迹混成一锅。
- 设计冲突流水线：契约/模块设计必须带结构化字段（对外 API、事件、实体、错误码、依赖方向）。Reconciler 先做确定性 diff（如同名异义、双向依赖、缺 owner），再 LLM 解释/提案，仍僵持则人升级。禁止静默压制冲突。
- v1 范围帽：端到端瘦切片；限制模块扇出；只覆盖可检测的结构化冲突类；优先可演示，而非一开始就做高深自动调和。
- 测试接缝（唯一对外接缝）：`run` 入口。支持可替换 LLM/工具端口与夹具仓库；测试断言外部行为（产物 + RunResult），不断言节点内部或 prompt 文本。
- 调用约定：目标仓路径可指定，默认当前工作目录。
- 本仓库元工作仍用本地 markdown issue tracker；本功能 spec 位于 `.scratch/multi-agent-coding-assistant/`。

## Testing Decisions

- 好测试只断言外部行为：给定目标与夹具仓（以及桩掉的模型/工具端口），`run` 接缝产出预期 run 产物、闸门暂停/恢复与 RunResult。不断言内部 LangGraph 节点名、prompt 内容或私有辅助函数。
- 唯一接缝：`run`（CLI 与库行为一致；优先测 CLI 所调用的库入口）。
- 至少覆盖：设计冻结 → 实现 → review → PR 草稿的快乐路径；确定性冲突检测生成冲突报告与调和输出；人闸暂停与批准后恢复；review 失败导致未成功直至修复或明确失败；检查失败路径；v1 扇出上限行为。
- 使用夹具仓库与假 LLM/工具响应（返回固定结构化设计/补丁），保证测试确定且不依赖联网调模型。
- 先例：本仓库尚无测试（绿地）。后续功能以 `run` 接缝验收测试为规范样式。

## Out of Scope

- 以 IDE / Cursor 侧栏或 GitHub App / Issue 触发托管运行为主入口（以后可包同一库）。
- 以自由多 Agent 群聊作为主设计对齐机制。
- 无人闸自动合入 main。
- 无限模块扇出、开放式冲突本体、以及超出计划扇出的自改写 org graph。
- 运行时依赖 `triage` skill 或完整 GitHub Issues 工作流（本仓库元工作用本地 markdown）。
- 知识图谱工程、多租户 SaaS 控制面、企业网关治理产品。
- 非编码域（个人助理、纯调研简报产品）作为一等模式。
- 保证模型质量；测试桩掉模型，验证编排与产物。

## Further Notes

- 词汇：本仓库尚无 `CONTEXT.md`。在领域建模落地前，沿用已锁定 grilling 用语：org graph、work graph、契约、模块设计、Reconciler、冻结设计、人闸、run 产物、混合隔离、PR 草稿。
