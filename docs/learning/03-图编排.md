# 03 — 图编排（Graph Engineering）

## 问题是什么

多 Agent 系统如果只回答「有哪些角色」，还不够。

还必须回答：

- 谁先做、谁后做？
- 什么时候可以并行？
- 失败走哪条路？
- 什么时候必须停下来等人？
- 谁有权改写最终设计？

如果这些都靠模型临场发挥，系统会变成：

> 一群有职称的 Agent，在一个没有议程的会议室里聊天。

**Graph Engineering** 的核心主张是：

> 把组织结构、工作流程、权限边界写进可执行的图里；  
> Agent loop 可以发生在节点内部，但不能替代整张图。

## 三张图分别是什么

### 1. 组织图（Org Graph）

长期稳定的角色编制。

本仓库固定六类：

1. Orchestrator — 规划本次工作
2. Contracts — 写薄共享契约
3. Module Designers — 按模块设计
4. Reconciler — 冲突检出与冻结设计
5. Implementers — 隔离写码
6. Reviewer — 检查与 PR 草稿

组织图解决的是：**职责边界**，不是某一次任务细节。

### 2. 工作图（Work Graph）

这一次请求的任务安排。

例如这次模块是 `orders` + `inventory`，下一次可能是 `posts` + `comments`。

角色种类不变，但模块集合、步骤焦点会变。

当前会落盘为 `work_graph.json`。

诚实说明：v1 里它更像**规划产物**；真正驱动执行的拓扑基本是固定的，还没有「根据 work_graph 动态生成全新 LangGraph」。

### 3. 执行图（Execution Graph）

代码真正跑的那张图：节点、边、条件分支、暂停点。

本仓库用 LangGraph 表达，大致路径：

```text
Orchestrator → Contracts → Module Designers → Reconciler
  → 设计冻结闸
  → Implementers → Reviewer
  → 合入闸
  → completed
```

还有失败与打回分支，例如：

- 设计被拒 → `rejected_design`
- 实现失败 → `failed`
- Review 失败且找到 owner → 打回对应 Implementer
- Review 失败且找不到 owner → `review_failed`

## 常见方案对比

| 方案 | 流程由谁决定 | 适合 |
|---|---|---|
| 纯 Agent loop | 模型工具调用循环 | 单任务探索 |
| 自由多 Agent 群聊 | 对话动态 | 头脑风暴 |
| 固定脚本流水线 | 程序员写死顺序 | 简单 ETL |
| 图编排 | 代码定义拓扑 + 状态决定分支 | 要治理的多角色系统 |

图编排相对脚本的好处是：**同一条业务里可以有暂停、重试、打回、升级**，而不只是直线。

相对群聊的好处是：**下一步合法动作是有限集合**，可测试、可推理。

## 我们怎么做

- 用 LangGraph 固定执行拓扑（`MacsGraphRunner._build_graph`）
- 用 `phase` 做路由，避免终态 resume 又从头规划
- 人闸处结束图执行；`resume` 注入 `decision` 再继续
- auto 模式不改图语义，只在外层自动投批准票

一句话：

> **loop 在节点内，治理在图上。**

## 代码 / 实验在哪

- 建图与路由：`src/macs/pipeline.py`（`_build_graph`、`_route_target`、`_after_*`）
- 工作规划产物：`work_graph.json`
- 规格中的 Graph Engineering 表述：`.scratch/multi-agent-coding-assistant/spec.md` Solution / Implementation Decisions

建议实验：

```bash
# 交互：观察两道闸如何把一张图切成可恢复的多段
macs run "x [modules: a, b]" --repo /tmp/macs-graph
macs resume <run_id> --repo /tmp/macs-graph --approve
macs resume <run_id> --repo /tmp/macs-graph --approve
```

每段结束后看 `status.json` 的 `phase` / `gate`，对照「执行图停在了哪」。

## 还缺什么

- Work Graph 尚未真正驱动动态拓扑
- 模块设计扇出仍是串行循环，不是图级并行
- 节点内部还不是完整 tool-using agent loop（实现只是一跳 LLM 写文件）

这些不影响「为什么需要图」这个理论点，但说明本仓库仍是 **Graph Engineering 的瘦切片演示**。
