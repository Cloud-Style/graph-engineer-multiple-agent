# 01 — 为什么多 Agent 会失控？

## 问题是什么

很多人第一次接触多 Agent，直觉是：

> 一个 Agent 不够强，那就多叫几个。

但多 Agent 真正难的地方，通常不是「模型聪不聪明」，而是**协作是否可治理**。

如果没有设计，多个 Agent 一起干活时，常见会失控在这些点上：

1. **角色混乱**：同一个主体既规划、又设计、又写码、又审自己
2. **上下文过载**：所有历史、约束、文件、失败信息塞进一次对话
3. **决策不可追溯**：事后说不清谁决定了接口长什么样
4. **互相覆盖**：两个 Agent 同时改同一份工作区
5. **讨论不收敛**：一直聊、一直总结，但没有可交付产物
6. **责任不清**：出了问题不知道该打回谁

单 Agent 也会有一部分问题（尤其是上下文与自我审查），但多 Agent 会把「协作」放大成一等公民问题。

## 常见方案

| 思路 | 做法 | 优点 | 风险 |
|---|---|---|---|
| 更强的单 Agent | 一个大模型 + 工具循环做到底 | 简单 | 角色混、难审计、难并行 |
| 自由群聊 | 多个 Agent 互相发消息 | 灵活 | 难测、难收敛、难恢复 |
| 主管—下属 | Supervisor 派工并汇总 | 比群聊可控 | Supervisor 成瓶颈 |
| 工程化编排 | 固定角色、显式流程、正式产物 | 可测可恢复 | 前期要设计协议 |

## 我们怎么做

本仓库选择第四种：**先承认多 Agent 会失控，再用工程约束把它管住。**

具体约束包括：

- 固定六类角色，不允许实现者顺便当审查者
- 用图规定执行顺序，而不是让 Agent 自己决定下一步聊什么
- 用契约 / 设计 / 冻结设计等产物协作，而不是靠聊天记忆
- 写码进独立 worktree，避免直接互相覆盖
- 两道人闸：写码前、接受前
- 对外只暴露 `run` / `resume`，方便测试「系统行为」而不是「某次 prompt」

## 代码 / 实验在哪

- 角色与流程：`src/macs/pipeline.py`（`MacsGraphRunner`）
- 对外接缝：`src/macs/run.py`、`src/macs/cli.py`
- 产品动机（为什么要做）：`.scratch/multi-agent-coding-assistant/spec.md` 的 Problem Statement

建议实验：

```bash
macs run "add auth [modules: auth, api]" --repo /tmp/macs-demo
# 停在设计闸；看 runs/<id>/ 里是否已有 work_graph、contract、designs
```

观察：规划阶段已经落盘，但还没有 worktree——因为人还没批准设计。

## 还缺什么

- 角色分离在代码里是「不同节点 + 不同 prompt」，还不是多个长期存活的 Agent 进程
- 真正并行扇出尚未做成 LangGraph `Send` 式并发
- 本文只回答「为什么要管」；「怎么通信 / 怎么解冲突」见后续文章
