# 04 — 冲突：多 Agent 会争什么，怎么处理

## 1. 问题是什么

多 Agent 不只会「一起把事做完」，还会「一起把事做拧」。

冲突至少有四类，不要混为一谈：

| 类型 | 例子 | 若不管会怎样 |
|---|---|---|
| 需求冲突 | 库存不足该失败还是部分成功 | 做出来的系统行为不一致 |
| 设计冲突 | 同名 API 两种 shape；双向依赖 | 实现阶段互相假设崩掉 |
| 写入冲突 | 两个 Agent 改同一文件 | 覆盖、脏合并、来源不清 |
| 责任冲突 | 检查挂了但不知道打回谁 | 全局重写或乱修 |

「冲突解决」不是单靠模型和解，而是先**分类**，再选机制。

## 2. 常见方案

### 只靠 LLM 读两份设计然后「总结一下」

- 优点：实现快
- 缺点：不稳定、难测、可能静默抹掉分歧

### 只靠人开会

- 优点：重大架构可靠
- 缺点：贵、慢；所有小冲突都升级会拖垮流程

### 确定性规则 + LLM 提案 + 人裁决

- 程序先抓能抓的硬冲突（稳定、便宜、可测）
- LLM 解释并给合并方案
- 仍僵持或高风险 → 人闸

这是工程上较常见的分层。

### 用隔离避免写入冲突

设计一致也不够：两个写者同时改同一工作树，仍会物理打架。  
隔离（分支 / worktree）把写入冲突推迟到合并阶段，而不是假装它不存在。

## 3. 我们用的是什么？

### 设计冲突：结构化字段 + 确定性检测 + Reconciler

契约/设计带结构化字段：`apis`（name/owner/shape）、`dependency_direction` 等。

`detect_conflicts` 当前识别：

1. 同名 API、不同 shape
2. 双向依赖
3. API 缺 owner / owner 不在模块集合

有冲突时 Reconciler 调 LLM 提案，写入 `frozen_design.json`；冲突列表仍保留在 `conflicts.json`，**禁止静默删除记录**。

最终仍过设计冻结人闸。

### 写入冲突：隔离 worktree

每个实现任务独立分支与 worktree，不直接改同一工作目录。

### 责任冲突：按契约 API owner 打回

Review / `macs_check` 失败时，根据契约 owner 映射到任务 id。  
映射不到 → 显式失败，**禁止 queue-first**（随便扔给队列第一个）。

## 4. 为什么你真实跑秒杀时「没有冲突」？

因为检测器只认上面几类**硬冲突**。

若两个模块 API **名字不重叠**、依赖也只有单向，程序会诚实报告：`conflicts: []`。

这不等于设计完美，只等于：

> 没有命中当前规则。

软冲突（`productId` vs `sku`、同步 vs 异步语义未体现在同名 API 上等）目前基本检不出。

## 5. 代码 / 实验在哪

- 检测：`src/macs/conflict.py`
- 调和与冻结：`src/macs/pipeline.py` 的 `_reconciler`
- 失败路由：`_task_ids_for_contract_owners`、`_reviewer`
- 隔离写：`src/macs/worktree.py`

建议实验（离线强制硬冲突）：

```bash
macs run "x [modules: orders, inventory] [conflict:api]" --repo /tmp/macs-conflict
cat /tmp/macs-conflict/runs/*/conflicts.json
```

再用真实模型时，若想看到冲突，需要让两边**故意声明同名 API 且 shape 不同**，或形成双向依赖——否则模型常会「自觉分工」避开硬冲突。

## 6. 还缺什么

- 实体字段差异、语义对齐、幂等与事务边界等软冲突本体
- 多 worktree 之后的自动合并冲突处理
- 更强的「冲突升级给人」交互（目前主要靠闸门批准/驳回）
